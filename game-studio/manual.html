KUROGAMES GAME DEVELOPMENT STANDARD / VERSION 1.0

ゲーム制作マニュアル

ゲームの楽しさや豪華な演出は妥協せず、裏側の通信・データ処理・同期を最適化するための共通規格です。新しいゲームの制作、既存ゲームの改修、オンライン機能の追加は、このマニュアルを基準にします。

🎮 楽しさ優先ゲーム性と演出を弱めない
⚡ 即時反応ローカルでできる表示は先に反映
📡 低通信必要なデータだけを必要な時に送る
🛡️ サーバー検証勝敗・権限・重要状態はサーバー確定
🧩 共通化既存SDK・共通機能を再利用

SDKの配信URL・バージョンは公開時点のStudio共通設定に合わせる。例のキャッシュ文字列を永続的に固定せず、SDKを更新したらHTML側の参照も同期する。

利用可能 ログイン済み

サーバーがSupabase Authのアクセストークンを検証し、内部ユーザーIDを確定します。プロフィール名やクライアントから送られたuserIdで本人確認しません。

オフライン動作 未ログイン

SDK初期化時にオンライン機能がfalseでも、CPU戦・ローカルゲーム・ローカル設定を遊べる設計にします。オンライン操作だけログイン案内を表示します。

オンライン対戦・オンラインランキング・クラウド保存はKUROアカウントへのログインが必要です。匿名Auth・ゲストトークン・ゲーム独自の認証方式は追加しません。

04即時反応・先行反映（Optimistic UI）

押した瞬間の反応を大切にします。ただし、画面上の仮反映とサーバー確定を混同しません。

操作
→
ローカルUIを即更新
→
裏で送信
→
確定 / 復元

推奨パターン

const previous = state.likes;
state.likes = previous + 1;
render(); // 先に表示を更新

try {
  await KuroGames.social.like(targetId);
  // サーバー成功。表示はそのまま
} catch (error) {
  state.likes = previous; // 失敗したら元に戻す
  render();
  showError("反映できませんでした。もう一度お試しください。");
}

上は動作イメージです。social.likeは説明用の仮名であり、現行SDK APIではありません。各ゲームでは実際に存在するSDKメソッドだけを使用してください。

操作先行反映確定の扱い
タブ・メニュー・選択・演出すぐ反映ローカルで完結
準備OK・投票すぐ押下状態を表示サーバー受付後に確定。失敗時は戻す
カードを出す・ターン操作移動演出や仮表示を先に行ってよいサーバーが合法手とターンを検証するまで確定扱いにしない
購入・ポイント・勝敗・ランキング処理中表示や仮演出は可サーバー確定前に残高・勝利・報酬を確定しない
UI状態は pending → confirmed または pending → rejected → rollback と区別します。オンラインアクションの再送では同じactionIdを再利用し、二重処理を防ぎます。

05演出・パフォーマンス規格

アニメーションを特に減らさない。 見た目を簡素化して軽くする方針は採用しません。勝利演出、パーティクル、カード移動、スライド、揺れ、光、コンボ、フィーバーなどはゲーム体験に必要なら自由に使います。

維持するもの

  • 勝利・敗北・レベルアップ演出
  • 画面遷移・スライド・フェード
  • パーティクル・光・揺れ・コンボ
  • カード・ピース・キャラクターの動き
  • ゲーム固有の派手な演出・音

最適化するもの

  • 同じデータやDOMを何度も作り直さない
  • 1フレームごとにサーバーへ通信しない
  • 使い終えたタイマー・イベントを解除
  • 画像・音声・アセットを適切に読み込む
  • 同じ演出の重複計算を避ける

軽量化は原則として実装の効率化で行います。演出の数・長さ・派手さを勝手に削る変更はしません。端末負荷が高い場合は、ゲーム性や主要演出を保ったまま段階的な品質調整を検討します。

🌐 公開データ

参加者全員に見せてよい盤面、公開ターン、公開スコア、公開プレイヤー一覧。

room state / public event

👤 個人専用

本人の手札・役職・秘密目標・本人だけの選択など。他の参加者へ送らない。

専用APIが必要

🔒 サーバー専用

山札全体、全員の秘密情報、乱数シード、不正検出情報。ブラウザへ返さない。

サーバー側に保持
重大： 現行の room.getState() はルーム参加者全員が取得できる共有状態です。手札・秘密役職を入れてはいけません。個人専用状態APIとサーバー専用状態管理が整っていないゲームは、秘密情報を必要とする対戦を安全に公開できると判断しないでください。

07Supabase通信規格

Supabaseを使うゲームも、接続・認証・データ保存の入口はKuroGames共通SDKに統一します。

データ / 操作通信タイミングルール
プロフィール必要時・キャッシュ失効時ユーザー切替時はキャッシュを分離・破棄
ランキング初回表示・更新時必要件数だけ取得。全件取得しない
ルーム作成・参加押下時に1回サーバーで参加条件・満員・重複を検証
ゲーム操作状態が変わる操作だけ操作差分だけを送信。毎フレーム送らない
ゲーム結果結果確定時同じ試合は同じsubmissionIdで一度だけ登録
設定・クラウド保存変更時・チェックポイント入力ごとの連続保存を避ける
演出・カーソル・選択途中原則通信なしブラウザ内で処理
通信量を減らす標準ルール
  • 画面再表示のたびに同じデータを取り直さない。キャッシュを再利用し、更新対象だけ取得する。
  • 必要な列・行・件数だけ読む。ランキングや履歴で全件SELECTしない。
  • 短い文字入力などはdebounceし、まとめられる設定更新はまとめる。
  • ゲーム中の演出やドラッグ位置をDBに保存しない。
  • Realtimeを使う場合は必要なルーム・イベントだけ購読し、画面離脱時に解除する。
  • 500msごとの常時ポーリングを標準にしない。イベント通知を優先し、ポーリングは必要時の補助にする。
  • 読み取りと書き込みを区別し、書き込みの再送には重複防止IDを付ける。
Supabaseクライアント直書きの禁止
ゲームHTMLごとにSupabaseクライアントを新規作成し、ランキング・ルーム・アカウント情報を直接書き換える設計は禁止します。既存の共通SDK・認証ブリッジ・Cloudflare通信経路を使用します。Service Roleキーや秘密鍵をフロントエンドに含めてはいけません。

08オンラインマッチング規格

マッチングは「待機中」の表示だけでは完成ではありません。キュー登録からルーム割当、接続確認、準備、開始、キャンセル、離脱、復帰、期限切れまでを一つのライフサイクルとして設計します。

現行実装との区別： 現在のSDKには大富豪系の findRandomMatch()、UNO用の findUnoRandomMatch(ruleMode) とステータス・キャンセルAPIが存在します。Edge Functionはゲーム別RPCへ振り分けています。七並べにも専用アクションがあります。これらは「全ゲーム共通の汎用マッチングAPI」ではありません。新しいゲームで既存関数をそのまま流用せず、専用バックエンド対応の有無を確認してください。

各状態から cancelled / expired / failed / disconnected へ遷移する条件も実装します。画面上の表示とサーバーの状態を一致させます。

8.2 マッチング条件
条件標準ルール
gameIdゲームIDを必ず分離。別ゲームのキューを混ぜない
mode / ruleModeルールモード・難易度・公式/ローカル等を一致させる
rulesetVersion互換性のないルールバージョンを混ぜない

skill / region必要なゲームだけ利用。待機が長い場合は段階的に条件を広げる
party / teamグループ参加を実装する場合はパーティー単位で割り当てる
8.3 標準的なマッチング手順
  1. 参加ボタン： 画面はすぐ「相手を探しています」に切り替える。二重押しを止める。
  2. キュー登録： SDK経由で1回送信。サーバーは認証・公開状態・multiplayer機能・条件・重複参加を検証する。
  3. 待機： joinを連打しない。statusを使って既存の待機状態を確認する。通信中のstatusは同時に1件まで。
  4. マッチ成立： サーバー側のトランザクションで参加者を確定し、ルームと参加者レコードを作成する。クライアントにルームを別々に作らせない。
  5. ルーム接続： 割り当てられたroomIdに接続し、接続できたプレイヤーだけACKする。SDKがACKするAPIではゲームから二重ACKしない。
  6. ロビー： 全員の参加状態を表示する。ReadyとStart投票は別の状態として扱う。
  7. 開始： サーバーが開始条件を再検証し、参加者一覧を固定してplayingへ移行する。
  8. 終了： サーバー確定結果を記録し、ルームを終了状態へ移す。ランキングは同じ試合IDで一度だけ反映する。
8.4 Ready / Startの共通ルール

人数が最大人数に達していなくても、ゲームの最小人数を満たしており、現在の参加者全員が開始を承認した場合は開始できる設計を標準とします。

項目意味動作
Ready参加準備ができた各プレイヤーがON/OFF。状態を全員へ共有
Start vote今のメンバーで開始したい全員の投票がそろったら開始条件を満たす
Start commitサーバーが開始を確定最小人数・全員Ready・全員投票・ルーム状態を再確認
  • 開始条件の基本式：参加人数がminPlayers以上、全員Ready、全員Start投票済み。
  • 誰かが退出・切断・新規参加した場合は開始投票をリセットし、残りの参加者に再確認する。
  • 開始確定時に参加者を固定し、以後の参加は拒否する。
  • ホストだけが独断で開始できる方式は、ゲームルールで明示的に必要な場合に限る。
8.5 キャンセル・切断・再接続
  • キャンセルボタンは即時にSearching表示を解除するが、サーバーの取消結果を確認する。マッチ成立と取消が競合した場合は、サーバーの最終状態に従う。
  • 待機中にページを再読み込みしても、新しいキューを重複作成せず、statusで既存の状態を復元する。
  • 一時切断と正式退出を区別する。再接続猶予中は同じルームに復帰させる。
  • 再接続時はルーム全体の公開スナップショットと本人に必要な個人データだけを取り直す。
  • タイムアウト・期限切れになったキューやルームはサーバー側で掃除する。クライアントが画面を閉じただけで永久に待機者を残さない。
現在の一時データ掃除では、待機キューは最終更新から2分経過すると削除対象、マッチ済みキューは15分のACK猶予などで整理されます。新しい汎用キューを導入する際は、待機中の有効性更新と実際のRPC挙動を確認し、UIのstatus更新間隔とDBの期限を揃えます。
8.6 キュー実装のサーバー要件
  • 同一ユーザーが同一ゲーム・同一モードで複数の有効キューに入れないよう、一意制約とトランザクションで防止する。
  • マッチ成立はDBトランザクション内で行い、同じ参加者が同時に別ルームへ割り当てられないようロックする。
  • roomId、status、matchedAt、ack状態をサーバー側で確定する。クライアント指定のuserIdを信用しない。
  • 満員・ルール不一致・ゲームID不一致・すでに別ルーム参加中の状態は明示的に拒否する。
  • キュー行は一時データとして期限切れ削除する。プロフィール・ランキング・ユーザー記録はキュー掃除の対象にしない。
  • 待機状況の通知はRealtime / DOイベントを優先。代替ポーリングは低頻度・バックオフ付き・in-flight重複禁止にする。
8.7 現行SDKで確認できるマッチングAPI
API対象状態
findRandomMatch()大富豪系の専用ランダムマッチ実装済み
getRandomMatchStatus()上記の待機状態確認実装済み

大富豪・UNOの既存APIはゲーム別RPCへ接続されています。七並べも専用のEdge Functionアクションがあります。新しいゲームは、汎用マッチング基盤が整うまで専用APIを追加するか、既存の専用対応ゲームに限定して利用します。メソッド名だけを見て任意のゲームで動くと判断しないでください。

09ルーム・リアルタイム同期

現在の共通ルームAPI

const room = await KuroGames.multiplayer.createRoom({
  maxPlayers: 4
});

// ルーム参加
const joined = await KuroGames.multiplayer.joinRoom("ABC234");

// 公開状態の取得・更新
const current = await room.getState();
await room.updateState(
  { phase: "lobby", publicPlayers: [] },
  current.updatedAt
);

// イベント受信
const offMessage = room.onMessage((event) => {
  // event.type / event.data
});

// 購読解除・退出
offMessage();
await room.leave();
項目共通仕様
ルームコード6文字英数字。読み間違いやすい文字を除外
人数2〜35人。maxPlayers既定値は4人
イベント名英数字・_・-、1〜40文字
イベントサイズ1イベントあたり32KB以内
状態競合updateStateにexpectedUpdatedAtを渡す。競合時は最新状態を取り直し再計算
リアルタイムCloudflare Durable Objects WebSocketを優先。SDK互換用にHTTPポーリング経路あり

イベントと永続状態を使い分ける

  • 一瞬の通知・演出・「誰かが準備OKを押した」通知はイベント向き。
  • 再読み込み後も必要なルーム状態や進行状態はサーバー側の状態保存を使う。
  • イベントだけを唯一の保存場所にしない。再接続時はスナップショットから復元する。
  • 参加者変更・ルーム終了・ゲーム終了時にすべての購読を解除する。
room.getState() / updateState() は全員に見える公開状態専用です。秘密の手札・役職・山札は保存しません。UNOのサーバー権威型機能などゲーム専用の安全な仕組みがある場合は、その専用APIを使用します。

10ランキング規格

現行SDKの登録・取得

// スコア登録
await KuroGames.ranking.submit(15000, {
  mode: "default",
  metadata: { difficulty: "normal" },
  submissionId: roundId
});

// 上位20件を取得
const rows = await KuroGames.ranking.get({
  mode: "default",
  limit: 20
});

submissionId は試合ごとのUUIDを使い、同じ試合の再送では同じIDを使います。SDKは指定IDが有効なら引き継ぎ、未指定・不正時のみUUIDを生成します。

ユーザー中心の統合ゲーム記録（実装済み）

全ゲームの記録はログイン中のユーザーIDに紐づき、ゲームID・モード別に分離して集計されます。勝敗・プレイ履歴・最高スコア・最速タイムを共通SDKから取得できます。

// 現在のゲームの記録
const gameStats = await KuroGames.stats.get({
  mode: "normal",
  limit: 100
});

// 自分の全ゲームの記録
const allStats = await KuroGames.stats.getAll({
  limit: 250
});

// 自分の最近のプレイ履歴
const history = await KuroGames.stats.history({
  allGames: true,
  limit: 50
});

ランキング送信およびサーバー検証済みの勝敗は統合記録にも自動反映されます。新しいゲームでは共通SDKを利用し、ゲーム固有の保存テーブルを新設しないでください。

集計上の注意：playsは保存済みの結果イベント数です。UNON・大富豪・人狼など過去データが勝利記録のみのゲームでは、敗北試合数を含みません。古い最高記録だけのデータからプレイ回数を推測して足すこともしません。

統合記録は本人の記録だけ取得できます。クライアントから記録テーブルへ直接書き込まず、共通API経由で保存します。

項目標準値・規則
機能有効化Studioのranking機能をONにする
modeランキング分類キー。異なるモードを混ぜない
limit既定20件、最大100件
score0〜1,000,000,000の整数
metadataオブジェクト、8KB以内。秘密情報を入れない
同点通常スコアは先に達成した記録を上位にする。最後も安定した順序を使う
重複防止gameId + userId + mode + submissionId等で二重加算を防ぐ
ランキング形式の例
  • ハイスコア： score降順。modeごとに分離。
  • 勝利数： 試合ごとの勝利を1件ずつ記録し、ユーザー単位で累計集計する。
  • 最速タイム： 小さい値が上位になるようサーバー側の並び順を定義する。上位20件を取得した後にブラウザで並べ替える方式は禁止。
  • Bot / Online： 公平性が異なる場合は別modeに分ける。
  • シーズン： シーズンIDをmodeまたは明確な分類キーで管理する。
不正対策： 現行のscore_submitには本人確認・数値/サイズ/頻度の基本検証がありますが、クライアントが申告したスコアの正しさを一般的に証明するものではありません。競技性の高い正式ランキングは、サーバー側でゲーム操作と勝敗を検証できるようにしてから接続します。クライアントから送った「勝った」「このスコアだった」だけで正式結果を確定しません。

11キャッシュ・保存規格

情報キャッシュ方針更新条件
ゲーム一覧・静的設定長めに保持公開情報更新時
プロフィール表示短〜中時間プロフィール編集・アカウント切替時
ランキング短時間保持試合終了・明示更新・TTL失効時
ルーム参加者・ターン古い値で確定しないイベント・再接続スナップショット
認証・権限古い状態を信頼しない親ページの認証ブリッジで再確認
演出・一時選択ブラウザ内だけゲーム状態に応じて破棄

保存のルール

  • クラウド保存は KuroGames.save.get/set/delete/list を利用する。
  • 設定変更・チェックポイント・ゲーム終了など、意味のあるタイミングで保存する。
  • 毎フレーム・毎ドラッグ位置・毎アニメーションフレームを保存しない。
  • アカウント切替時に前のユーザーのデータを次のユーザーへ表示しない。
  • ランキング・勝敗・課金相当のデータは単なるキャッシュを正本として使わない。

12エラー・再試行・復帰

状況標準対応
通信失敗状態を保持し、操作の種類に応じて再試行・復元する
401 / 認証失効認証ブリッジで再確認。未ログインならログイン案内
403 / 権限なし自動再試行しない。機能設定・参加権限を表示
409 / 状態競合最新状態を再取得し、操作を再計算。古い状態を上書きしない
二重送信同じactionId/submissionIdで重複排除
相手の切断一時切断として表示。ルールの猶予時間に沿って再接続

再試行の目安

1回目の一時エラー：少し待って再試行
2回目：待機時間を延ばして再試行
3回目：自動再試行を止め、利用者へ通知

実装では指数バックオフ＋ランダムな揺らぎを利用し、回数に上限を設定します。読み取りは再取得しやすい一方、書き込みは同じIDで重複排除できる場合だけ安全に再送します。入力内容や進行状況を失わせないようにします。

13セキュリティ必須規格

  • publicなどData APIに公開するスキーマの全テーブルでRLSを有効にする。
  • RLSは「ログイン済み」だけでなく、auth.uid()と所有者・ルーム参加者を照合する。
  • クライアントから渡されたuserId、username、KURO IDを本人確認・権限判定に使わない。
  • ユーザーが変更できるuser_metadataを認可判断に使用しない。
  • Service Roleキー・秘密鍵・サーバーチケット署名秘密をブラウザへ出さない。
  • ランキング、勝敗、ルーム参加者、準備状態など重要データをクライアントから直接自由更新させない。
  • イベント・共有ルーム状態・ランキングmetadataに秘密情報を含めない。
  • UPDATEポリシーはUSINGだけでなくWITH CHECKで所有者変更を防ぐ。
「ボタンを隠す」「CSSで非表示」「JSの変数名を難読化」はセキュリティ対策ではありません。重要な検証は必ずサーバー側で行います。

16人狼ゲームへの適用結果（専用実装）

共通基準を人狼ゲームへ適用した実装例です。これは人狼ゲーム専用の処理であり、すべての新作ゲームに使える汎用サーバールール実行環境が完成したという意味ではありません。

公開情報と秘密情報を分離

  • 共有ルーム状態にはプレイヤー一覧・生存状態・フェーズ・公開結果だけを保存。
  • 役職・投票先・夜行動・占い結果・霊媒結果はRLSで保護されたサーバー専用テーブルに保存。
  • 状態取得APIは本人の役職・本人向け結果だけを返し、人狼には人狼仲間の情報だけを追加で返す。全役職の公開はゲーム終了後のみ。

サーバー確定の操作・勝敗

  • 役職配布、役職確認、投票、集計、夜行動、襲撃・護衛、勝利判定をサーバー側で実施。
  • ホスト権限・参加者・フェーズ・生存状態・対象の合法性を操作ごとに検証。
  • 勝利が確定したときだけ勝者へ1勝を加算し、試合IDで二重登録を防止。
  • クライアントは共通ルームイベントで変更を通知し、各プレイヤーの専用状態を再取得する。再取得はイベントを主経路、30秒間隔を補完経路とする。
確認済み：3人対局の役職秘匿・投票・村人勝利・ランキング2件の登録、4人対局の占い結果秘匿・護衛成功・次フェーズ進行。いずれも一時DBデータをロールバックして検証。

実装ファイル：supabase/functions/kurogames-online/index.ts、supabase/migrations/20261123110000_werewolf_server_authority.sql、Studioに保存された人狼ゲームHTML。
