# KUROGAMES 共通オンライン・データ通信仕様

- 仕様書バージョン: 2.1
- 更新日: 2026-11-23
- 対象: KUROGAMES / KURO Lab のゲームプレイヤー、ゲームスタジオ、共通SDK、オンラインAPI、Cloudflare Workers、Durable Objects、Supabase
- 目的: ゲームごとの通信実装を統一し、個人データ・ルーム通信・ランキングを安全かつ一貫した方法で利用できるようにする

> **重要: この文書は「現在の実装」と「これから満たすべき完成仕様」を区別する。** 文書にAPIやルールが記載されていることは、そのAPIが既に本番実装済みであることを意味しない。各節の状態表示を確認すること。

## 0. 実装状態の表記

| 表記 | 意味 |
|---|---|
| 実装済み | 現在のSDK/APIに実装が確認できる |
| 一部実装 | 基本機能はあるが、セキュリティ・整合性・テストに不足がある |
| 今後実装 | 本仕様で定める完成要件。現時点では利用できない |
| 要確認 | デプロイ済み関数とGitHub上のソースの同期、または本番E2Eテストが未確認 |

## 1. 基本方針

1. ゲームHTMLは共通SDKを通して通信する。ゲームごとにSupabase URL、APIキー、認証処理、通信中継を個別実装しない。
2. ログインユーザーの識別は、サーバーがアクセストークンから検証したユーザーIDで行う。クライアントが送った userId、KURO ID、ユーザー名を本人確認に使わない。
3. 全プレイヤーに公開してよい情報と、本人だけに見せる情報を必ず分離する。
4. 手札、役職、山札、伏せたカード、秘密目標、未公開選択、秘密の乱数シードなどを共有ルーム状態や全員向けイベントに含めない。
5. ランキングに影響する勝敗・スコア・報酬の最終判定はサーバー側で行う。クライアントが送る「勝った」「スコアは100万だった」という申告だけでランキングを確定しない。
6. 通信経路の内部実装にかかわらず、ゲーム側のSDK呼び出し・戻り値・エラー仕様を統一する。
7. 通信の再送、二重クリック、切断、再接続、複数人の同時操作を前提に設計する。
8. 秘密情報をブラウザに送った後は、プレイヤー本人が開発者ツールで確認できる。したがって「本人に見せる必要のない情報」は、本人のブラウザにも送らない。

## 2. 全体アーキテクチャ

通常の通信経路は次の通り。

1. KUROGAMESのゲームプレイヤーがゲームHTMLを表示する。
2. ゲームHTMLが共通SDKを読み込む。
3. SDKが親ページの認証ブリッジからログインセッションを受け取る。
4. SDKがゲームID、操作内容、アクセストークンをオンラインAPIに送る。
5. Edge Functionがアクセストークンを検証し、ユーザーIDを確定する。
6. APIがゲームの公開状態、Studioの機能設定、ルーム参加状態、権限、データ形式、サイズ、回数制限を検証する。
7. APIが必要なデータだけを読み書きする。
8. SDKが結果をゲームに返し、必要な更新をCloudflare Durable Objectsによるリアルタイム通知、または必要な場合のHTTPポーリングで通知する。

### 2.1 API通信：Cloudflare Pages Functions

- ブラウザから同一オリジンの `/api/cloudflare-relay` を呼び出す。
- Cloudflare Pages Functionが許可されたSupabase REST/Auth/Storage APIおよび許可済みEdge Functionだけを中継する。
- 中継先・HTTPメソッド・ヘッダーはサーバー側で許可リストにより検証する。
- 認証はSupabaseのアクセストークンで行い、ユーザーIDや権限はサーバー側で確認する。
- Supabase Databaseは永続データの保存先として利用する。サービスロールキー等の秘密情報をブラウザへ渡さない。
- 旧通信経路やクライアント側の通信方式切り替えは使用しない。

### 2.2 ルーム通信：Cloudflare Workers + Durable Objects

- ルームのリアルタイム状態・イベント同期はCloudflare WorkerとDurable Objectsを利用する。
- Durable Objectがルーム単位の接続と状態更新を調整する。
- ルーム作成・参加認証など、既存の管理APIで処理している機能は担当APIの認証・権限検証を維持する。
- WebSocketを使用できない環境や旧SDKの互換経路ではHTTPポーリングをフォールバックとして扱う。ポーリングはリアルタイム通信と同等の即時性を保証しない。
- ゲーム側は接続先の選択や通信方式の分岐を行わず、共通SDKの同じメソッドを使う。

## 3. ゲームID・本人確認・機能設定

### 3.1 初期化

ゲームは、オンラインAPIを呼ぶ前に一度初期化する。

    const result = await KuroGames.init({
      gameId: "Studioに表示されるゲームID"
    });

    console.log(result.features);

- gameIdはKUROGAMES Studioに登録された公開ゲームのIDを使用する。
- 初期化が失敗した場合、オンライン機能を成功したものとして扱わない。
- 初期化完了前にsave、ranking、multiplayerを呼ばない。
- ゲームIDを別ゲームのものに差し替えて他ゲームのデータへアクセスできないよう、APIはゲームIDと公開状態を毎回検証する。

初期化の戻り値:

    {
      gameId: "ゲームUUID",
      game: {
        id: "ゲームUUID",
        title: "ゲーム名",
        slug: "ゲーム識別子"
      },
      features: {
        ranking: true,
        cloudSave: true,
        multiplayer: true
      }
    }

### 3.2 認証情報

- userIdはアクセストークンを検証したサーバーが決定する。
- kuroId、username、displayNameはプロフィール表示用情報であり、認証・権限判定の根拠にしない。
- APIリクエスト本文のuserIdを本人確認に使用しない。
- KURO IDやユーザー名を変更されても、内部のユーザーIDによるデータ所有関係を維持する。
- ログアウト・アカウント切替後は、古いユーザーのデータを新ユーザーに表示しない。

### 3.3 Studioの機能フラグ

| フラグ | 用途 | 有効時に使えるAPI |
|---|---|---|
| ranking | スコア・勝利回数ランキング | ranking.submit / ranking.get |
| cloudSave | 個人クラウドセーブ | save.get / set / list / delete |
| multiplayer | ルームと複数人通信 | multiplayer.* |

- フラグがOFFなら、対象APIはサーバー側で拒否する。画面上でボタンを隠すだけでは不可。
- フラグはゲームごとに独立させる。
- StudioのON/OFFは保存直後からAPIのアクセス判定に反映する。
- Werewolfでランキングを使用する場合、Studio側のrankingをONにする必要がある。過去の設定記録ではranking=falseだったため、本番設定値を別途確認する。

## 4. データの公開範囲を3種類に分ける

この分類はKUROGAMESオンラインゲームの必須ルールとする。

### 4.1 公開ルームデータ（全参加者に見えてよい情報）

保存先: 現行の game_online_rooms.game_data

例:
- 現在のゲームフェーズ
- 公開済みの場札・盤面
- 公開スコア
- 公開ターン番号
- プレイヤー一覧、公開プロフィール
- 全員に公開済みのゲーム結果
- 制限時間や公開ルール設定

注意:
- 現行のroom.getState()はルーム参加者全員が同じJSON状態を取得する。
- このデータを見れば、参加者は内容を読むことができる。
- CSSで非表示にしても秘密にはならない。
- JSONのキー名を難読化しても秘密にはならない。

### 4.2 個人専用データ（本人だけが取得できる情報）

完成仕様の保存先: room_idとuser_idを組み合わせて権限分離した個人状態領域。

例:
- 本人の手札
- 本人だけが見る役職
- 本人だけの秘密目標
- 本人に配布された非公開情報
- 本人だけの選択途中データ

必須条件:
- APIはアクセストークンから本人のuserIdを特定する。
- リクエスト本文に別ユーザーのuserIdを指定しても、そのユーザーの個人データは返さない。
- ルーム参加者であることも確認する。
- 他人の個人状態を取得するAPIを一般クライアント向けに提供しない。
- Realtimeの全員向けbroadcast、room.send、room.getStateに個人秘密を含めない。
- サーバーから本人へ返すレスポンスも、本人の情報だけに限定する。
- ブラウザに届いた本人の手札は本人が開発者ツールで確認できる。それは防止対象ではない。他人の手札が本人の通信に含まれないことが目的。

### 4.3 サーバー専用データ（クライアントに返さない情報）

完成仕様の保存先: サーバー専用列またはRLSで完全に保護したサーバー専用テーブル。

例:
- 山札全体、まだ配られていないカード
- 全員の手札を含む完全なゲーム状態
- 人狼などの非公開役職割当
- 秘密の乱数シード
- 未公開の正解・イベント
- 不正検出用データ
- サーバーが検証するための状態履歴

必須条件:
- クライアント向けAPIの返却JSONに含めない。
- 公開ルーム状態にコピーしない。
- ルームイベントに含めない。
- SupabaseのサービスロールキーはEdge Functionの環境変数だけで扱う。
- DBのRLSで一般クライアントから直接読めないようにする。
- サーバー専用データを返すデバッグAPIを本番に公開しない。

### 4.4 現在の重大な制約

現行のroom.getState() / room.updateState()は、ルーム全体で共有する状態を読み書きするAPIである。参加者の手札や秘密役職をこの状態に格納すると、他の参加者も取得できる。

したがって、個人専用状態APIとサーバー専用状態管理が実装されるまでは、秘密情報を必要とするゲームでroom.getState()に秘密情報を保存してはならない。人狼・カードゲームなどで秘密情報を使う場合は、非公開情報を分離する改修が完了するまで「安全な対戦用」として公開しない。

## 5. 共通SDK API仕様

## 5.1 クラウドセーブ

実装済みAPI:

    await KuroGames.save.set("progress", {
      stage: 12,
      coins: 450
    });

    const value = await KuroGames.save.get("progress");
    const list = await KuroGames.save.list({ limit: 100 });
    await KuroGames.save.delete("progress");

データの分離単位:
- gameId
- 認証済みuserId
- save key

制限:
- 1キー64KB以内
- キー名は1〜64文字
- listの取得件数は最大100件
- 未保存キーのgetはvalue=null
- 他ユーザーのセーブを読み書きできない
- cloudSave=falseなら拒否

save.getの戻り値:

    {
      value: { stage: 12, coins: 450 },
      updatedAt: "2026-11-20T10:00:00.000Z"
    }

save.setの戻り値:

    {
      ok: true,
      updatedAt: "2026-11-20T10:00:00.000Z"
    }

save.listの項目:

    [
      {
        save_key: "progress",
        updated_at: "2026-11-20T10:00:00.000Z"
      }
    ]

save.deleteの戻り値:

    { ok: true }

KuroGames.storageはKuroGames.saveの別名であり、別の保存領域ではない。

    KuroGames.storage.get(key)
    KuroGames.storage.set(key, value)
    KuroGames.storage.remove(key)
    KuroGames.storage.list(options)

## 5.2 ルーム作成・参加

実装済みAPI:

    const room = await KuroGames.multiplayer.createRoom({
      maxPlayers: 35
    });

    // または
    const room = await KuroGames.multiplayer.joinRoom("ABC234");

仕様:
- ルームコードは6文字英数字。
- 使用文字は読み間違いを避けるため一部文字を除外する。
- 参加人数の範囲は2〜35人。
- maxPlayersの既定値は4人。
- ルームはgameId単位で分離する。
- 参加時にサーバー側で満員・終了済み・期限切れ・ゲームID一致・重複参加を検証する。
- 参加者の追加・退出・タイムアウトをサーバーが管理する。
- ルームIDやroomCodeだけを知っていても、参加権限を得られない。
- 他ゲームのルームへ参加できない。

代表的なroom情報:

    {
      id: "ルームUUID",
      game_id: "ゲームUUID",
      room_code: "ABC234",
      host_user_id: "ホストの内部ユーザーID",
      max_players: 35,
      player_count: 3,
      status: "waiting"
    }

プレイヤー一覧の表示用情報:

    {
      userId: "内部ユーザーID",
      kuroId: "KURO-...",
      displayName: "プレイヤー名",
      joinedAt: "日時"
    }

userIdは内部識別用であり、画面に表示する必要はない。表示名とKURO IDはプロフィール情報として扱い、権限判定には使わない。

## 5.3 公開ルーム状態の取得

実装済みAPI:

    const result = await room.getState();

戻り値は次の1形式に統一する。

    {
      state: {
        phase: "lobby",
        publicPlayers: []
      },
      updatedAt: "2026-11-20T10:00:00.000Z",
      roomStatus: "waiting"
    }

フィールド:
- state: 全参加者に公開してよいゲーム状態。未保存ならnull。
- updatedAt: 最終更新時刻。未保存ならnull。
- roomStatus: waiting / playing / closed等のルーム状態。

重要:
- stateは公開情報専用。
- getStateの返却値を複数の形式として推測して読む必要はない。
- 将来フィールドを追加する場合も既存フィールド名の意味を変えない。
- 取得できたstateをそのまま秘密情報の保管場所に使ってはならない。

## 5.4 公開ルーム状態の更新

実装済みAPI:

    const current = await room.getState();

    const result = await room.updateState(
      {
        phase: "playing",
        publicPlayers: []
      },
      current.updatedAt
    );

第2引数expectedUpdatedAtは楽観ロック用である。

成功:

    {
      ok: true,
      conflict: false,
      updatedAt: "2026-11-20T10:00:05.000Z"
    }

競合:

    {
      ok: false,
      conflict: true
    }

競合した場合:
1. 競合を成功扱いしない。
2. 最新状態をgetStateで再取得する。
3. 最新状態に対して自分の変更を再計算する。
4. 新しいupdatedAtを渡して再試行する。
5. 一定回数失敗したらユーザーに再試行を案内する。

expectedUpdatedAtを省略した場合は、初回作成時など現在値がnullであることを期待する。複数人が同じ状態を同時に更新するゲームでは、必ず取得したupdatedAtを使う。

このAPIは公開状態の同期用であり、サーバーによるゲームルール判定を代替しない。クライアントが任意のstateを送れる状態のまま、勝敗や報酬の正しさを保証できると考えてはならない。

## 5.5 ルームイベント

実装済みAPI:

    await room.send("player-ready", {
      ready: true
    });

    const off = room.onMessage((event) => {
      console.log(event.type, event.data, event.from);
    });

イベント仕様:
- イベント名は英数字、アンダースコア、ハイフンのみ。1〜40文字。
- ペイロードは32KB以内。
- イベントは通知・演出・状態更新のお知らせに使う。
- 永続化が必要な状態をイベントだけに保存しない。
- 重要データはDB上のstateまたは専用APIに保存する。
- 全員向けイベントに個人秘密を含めない。
- 送信者IDはサーバー認証情報から設定する。クライアントが任意の送信者IDを偽装できないようにする。

受信イベントの標準形式:

    {
      type: "player-ready",
      data: { ready: true },
      from: "送信者の内部ユーザーID",
      sentAt: 1795168800000
    }

Realtimeではbroadcast、Cloudflare経由では保存イベントのポーリングを利用する。どちらも同じevent形式をSDKが返す。

## 5.6 プレイヤー一覧の変更通知

    const offPlayers = room.onPlayersChange((players) => {
      // 参加・退出・接続状態の変化を反映
    });

- 初回登録時にも現在の一覧を通知する。
- 購読解除関数を返す。
- プレイヤー情報は表示用の公開プロフィール情報に限定する。
- 他人の手札、役職、秘密状態をplayersに含めない。
- 一時切断と正式退出を必要に応じて区別する。

## 5.7 退出・購読解除

    off();
    offPlayers();
    await room.leave();

- 画面遷移、ゲーム終了、ルーム離脱時にイベント購読を解除する。
- leave後のsendやstate更新を成功扱いしない。
- 通信が切れた場合のheartbeat / timeout処理をサーバー側で行う。
- ブラウザを閉じただけでも参加者状態が永久に残らないようにする。

## 5.8 マッチメイキング（現行APIと共通規格）

### 5.8.1 現行SDK/APIの範囲

現在の共通SDKには、特定ゲーム向けのマッチングメソッドがある。

大富豪系：
```javascript
const result = await KuroGames.multiplayer.findRandomMatch();
if (result.status === "waiting") {
  // 待機中。joinを繰り返さず、status APIで状態を確認する
}
if (result.status === "matched") {
  // result.room が接続済み
}
```

- `getRandomMatchStatus()` は既存待機状態の確認に使用する。
- `cancelRandomMatch()` は待機の取消に使用する。
- このSDKメソッドは現在のEdge Functionで大富豪用RPC（`kuro_daifugo_matchmaking_*`）へ接続される。任意の新作ゲーム向け汎用APIではない。

UNO：
- `findUnoRandomMatch(ruleMode)`
- `getUnoRandomMatchStatus(ruleMode)`
- `cancelUnoRandomMatch()`
- `ruleMode` は `official` または `local`。モードが異なる参加者を混ぜない。
- 現在のEdge FunctionではUNO専用RPC（`kuro_unon_matchmaking_*`）へ接続される。

七並べ：
- `kurogames-online` Edge Functionに `sevens_matchmaking_join/status/cancel/ack` の専用アクションが存在する。
- 専用処理は2〜4人の参加者数とルーム人数の整合を確認する。
- 現行SDKの全ゲーム共通メソッドとして公開されているわけではない。新しいゲームがこの専用アクションを流用してはならない。

matched結果を返す現行SDKの接続ヘルパーは、ルームへの接続後に `matchmaking_ack` またはUNO用ACKを送る。ゲームHTMLから同じACKを重ねて送らない。接続・ACKの失敗を成功扱いせず、SDKとサーバーの最終状態を再確認する。

### 5.8.2 共通マッチングの状態モデル（全ゲーム共通の目標仕様）

汎用マッチングAPIは、今後の共通基盤として次の状態を扱う。ここに記載した汎用契約は設計基準であり、現在のSDKで全ゲームに提供済みという意味ではない。

| 状態 | 意味 |
|---|---|
| idle | キュー未参加 |
| waiting | 条件を満たす相手を検索中 |
| matched | サーバーが対戦グループとルームを確定 |
| connected | クライアントがルームへ接続し、ACK済み |
| lobby | メンバー一覧・Ready・Start投票を受け付ける |
| playing | サーバーが開始を確定 |
| finished | 結果確定・ルーム終了 |
| cancelled / expired / failed | 取消・期限切れ・エラー |

### 5.8.3 マッチング条件

最低限、サーバーは次を検証する。

- `game_id`：ゲーム単位でキューを分離する。
- `mode / rule_mode`：ルール・難易度・公式/ローカルの区分。
- `ruleset_version`：互換性のないルールバージョンを混在させない。
- `min_players / max_players`：ゲームの参加可能人数。
- 必要なゲームに限り、地域・スキル帯・チーム・パーティー条件を使う。待ち時間が長い場合はサーバーの方針で段階的に条件を広げる。

クライアントが送った `user_id` は本人確認に使わない。認証済みアクセストークンからサーバーがユーザーIDを確定する。

### 5.8.4 キュー登録・同時成立の必須要件

1. 参加要求を受けたサーバーは、認証・公開状態・multiplayer機能・入力条件・既存ルーム参加を検証する。
2. 同一ユーザーが同一ゲーム/モードで有効なキューへ二重登録されないよう、一意制約とトランザクションで守る。
3. 複数のマッチメーカーが同じ待機者を同時に確保しないよう、DBロックまたは同等の排他制御を使う。
4. 参加者確定・ルーム作成・メンバー登録・queueをmatchedへ更新する処理は、原子的に確定する。途中だけ成功した状態を作らない。
5. クライアントの `join` 再送は、既存の待機状態を返し、新しいキューや別ルームを重複作成しない。
6. マッチ成立後は、roomIdと割り当て参加者をサーバーが返す。クライアントが独自にルームを作り直さない。
7. ルーム接続の成功後にACKし、サーバーは参加者ごとの確認状態を追跡する。

### 5.8.5 待機中の通信

- 初回のjoinは1回だけ送信する。待機状態の確認にjoinを繰り返さない。
- 待機中はstatusを利用する。statusリクエストは同時に1件までとし、短い間隔の連続ポーリングを避ける。
- 通知を利用できる場合はRealtime / Durable Objectsのイベントを優先し、HTTPポーリングは低頻度の補助にする。
- 現在の一時データ掃除では、waitingのマッチング行は `last_seen_at` が2分以上古い場合に削除対象になる。新しい汎用キューを設計する際は、待機状態の有効性更新（heartbeat/touch）とstatus APIの役割をDB RPCまで含めて定義し、期限切れ削除と整合させる。
- matched行にはACKの猶予があり、現在のcleanup仕様では15分を超えた未完了行などを整理する。実際のACK猶予・再キュー規則はゲームごとに明示する。

### 5.8.6 Ready / Start

ReadyとStart投票は別状態とする。

- Ready：プレイヤーが参加準備できたことを示す。
- Start vote：現在のメンバーで開始する意思表示。
- 基本開始条件は、参加人数が `min_players` 以上、現在の全参加者がReady、現在の全参加者がStart投票済みであること。
- 最大人数に達していなくても、最小人数を満たし全員が承認すれば開始可能なゲームでは、その条件で開始してよい。
- 参加者の追加・退出・切断によりメンバー構成が変わった場合、Start投票をリセットし、再確認する。
- 開始要求はサーバーが現在のメンバー、Ready、投票、ルーム状態を再検証してから確定する。ブラウザのタイマーやホストの画面だけで開始確定しない。
- 開始時にメンバーを固定し、以後の新規参加を拒否する。

### 5.8.7 キャンセル・再接続・期限切れ

- キャンセルとマッチ成立が競合した場合、サーバーが確定した最終状態を返す。クライアントが取消済みと決めつけない。
- ページ再読み込み後は新規joinせず、まずstatusで既存キュー/マッチ状態を復元する。
- 一時切断と正式退出を区別し、ルールで定めた猶予時間中は同一roomIdへ再接続させる。
- ルーム終了、期限切れ、ACK失敗、プレイヤー離脱後の再キュー可否をゲームごとに定義する。
- 一時キュー・待機ルームはサーバーのcleanupで削除する。プロフィール・ランキング・クラウドセーブなど永続データを誤って削除しない。

### 5.8.8 汎用APIの実装状態

現時点で全ゲームから利用できる汎用 `KuroGames.matchmaking.join/status/cancel` 契約は未実装。新規ゲームで必要な場合は、共通SDK、Edge Function、DB RPC、キューの一意制約、ルーム割当、ACK、cleanup、テストを一式で実装してから利用可能とする。ゲーム専用の関数を名前だけ変えて流用しない。

room.getStateでは秘密情報を安全に分離できないため、個人専用APIを追加する。

SDK案:

    const privateData =
      await room.privateState.get();

    await room.privateState.set({
      hand: ["card-a", "card-b"],

4. userIdが対象ルームの現参加者であることを確認する。
5. 保存時はそのuserIdの領域だけを更新する。
6. 取得時はそのuserIdに対応する個人データだけ返す。
7. リクエスト本文のuserIdを検索条件として信用しない。
8. 他人のuserIdを指定するパラメータ自体を一般APIに設けない。
9. 取得・更新の両方でサイズとJSON構造を検証する。
10. 退室後・ルーム終了後のアクセス方針を明示し、不正な再取得を防ぐ。

DB設計案:
- game_id
- room_id
- user_id
- payload
- updated_at
- room_id + user_idを一意制約にする。
- RLSは一般クライアントからの直接読み書きを禁止し、Edge Functionだけが必要な範囲で操作する。

個人専用APIのテスト:

- AさんがBさんのuserIdを指定してもBさんの手札を取得できない。

- Aさんがroom.getStateを何度実行しても、Bさんの秘密情報が混ざらない。

## 7. サーバー側ゲーム判定API（今後実装・ランキング対象ゲームで必須）

### 7.1 基本方針

ランキングや勝敗が重要なゲームでは、クライアントは「行動要求」を送るだけにする。クライアントが送る最終勝敗・勝利陣営・報酬量をそのまま採用しない。

SDK設計案:

    const result = await room.action({
      actionId: crypto.randomUUID(),
      type: "play-card",
      payload: {
        cardId: "card-a"
      },
      expectedVersion: 18
    });

上記は設計案であり、現行SDKのroom.actionとして実装済みではない。

### 7.2 サーバーの検証項目

各操作について次を検証する。

1. アクセストークンとアカウント
2. 公開済みゲームIDと機能設定
3. 対象ルームの存在・状態・期限
4. 操作者が参加者であること
5. 操作可能なフェーズであること
6. 操作者のターンであること
7. 操作内容がゲームルール上合法であること
8. 必要なカード・アイテム・ポイントを本人が所持していること
9. 既に使用済み・消費済みではないこと
10. expectedVersionが最新であること
11. actionIdが過去に処理されていないこと
12. 送信頻度・ペイロードサイズが上限内であること

検証に失敗した操作は状態を一切変更しない。エラー理由を安全な範囲で返し、不正な要求を成功レスポンスに変換しない。

### 7.3 原子的な更新

一つの行動は、可能な限りDBトランザクション内で次を一括処理する。

- actionIdの重複確認
- ルームバージョンの確認
- 行動ルールの検証
- サーバー専用状態の更新
- 公開状態の更新
- 個人専用状態の更新
- ターン・フェーズの更新
- 勝敗確定
- ランキング記録

途中だけ成功する状態を作らない。処理結果をactionIdに紐づけ、同じ要求が再送されても二重にカードを消費したり、二重に勝利数を加算したりしない。

### 7.4 乱数・配布・役職割当

- 山札シャッフル、役職割当、秘密イベントなどはサーバー側の安全な乱数を使用する。
- クライアントに乱数シードや山札全体を送らない。
- クライアントから受け取った配布結果を正しいものとして採用しない。
- サーバーは完全な内部状態を保持し、公開情報と本人向け情報を必要な相手にだけ返す。

### 7.5 勝敗の確定

- 勝敗はサーバーのゲームルール実装が確定する。
- クライアント側の画面表示は、サーバーの確定結果を表示する役割に限定する。
- クライアントが勝敗画面を改ざんしても、ランキングは変わらない。
- ルーム終了処理とランキング登録は同一の確定処理から実行する。
- 同じ試合の結果は一度だけ記録する。

### 7.6 ゲームごとのルール実装

ゲームごとにルールが異なるため、共通基盤は認証、参加者確認、ロック、履歴、重複防止、配信を担当し、ゲーム固有の合法手・勝敗判定はゲーム別サーバーモジュールで実装する。

ゲーム固有モジュールがないゲームを、サーバー検証済みゲームとして扱ってはならない。

## 8. ランキング仕様

### 8.1 現在のSDK API

ランキング登録:

    await KuroGames.ranking.submit(15000, {
      mode: "default",
      metadata: {
        difficulty: "normal"
      }
    });

ランキング取得:

    const rows = await KuroGames.ranking.get({
      mode: "default",
      limit: 20
    });

- ranking=trueのゲームだけ利用可能。
- modeはランキング分類キー。
- limitの既定値は20、上限は100。
- scoreは0〜1,000,000,000の整数。
- metadataはオブジェクトで8KB以内。
- 現行APIには短時間の送信回数制限がある。
- ranking.getは順位表データを返すAPIであり、ゲーム内の表示画面そのものはゲーム側で作る。

### 8.2 ranking.getの戻り値

SDKは配列を返す。

    [
      {
        rank: 1,
        score: 15000,
        mode: "default",
        createdAt: "2026-11-20T10:00:00.000Z",
        user: {
          kuroId: "KURO-...",
          username: "player",
          display_name: "プレイヤー",
          avatar_url: null
        }
      }
    ]

- rankは取得結果内の順位。
- scoreはランキング値。
- modeは対象モード。
- createdAtは記録日時。
- userは公開用プロフィール情報。
- 認証トークン、メールアドレス、非公開プロフィールを返さない。

### 8.3 通常スコアランキング

標準ルール:
1. scoreの降順。
2. 同点の場合は先に達成した記録を上位にする。
3. さらに同じ場合は一意で安定した順序を使う。
4. 表示上の順位とAPI上の順位を一致させる。
5. 別modeのスコアを混ぜない。

### 8.4 累計勝利数ランキング

人狼のような累計勝利数は、各試合の勝利を1件として記録し、ユーザーごとに集計する。

使用mode:
- werewolf_villager_wins: 村人陣営で勝利した回数
- werewolf_wolf_wins: 人狼陣営で勝利した回数

記録ルール:
- 勝利したプレイヤーだけにscore=1を加算する。
- 敗北者・観戦者・途中退出者には勝利を加算しない。
- 勝利陣営に属していた本人だけを加算対象にする。
- 1試合・1ユーザー・1勝利モードにつき一度だけ登録する。
- 同じ試合結果のリクエストを再送しても二重加算しない。
- 陣営ごとに別のランキングとして取得・表示する。
- 順位はユーザー単位の累計値で集計し、試合ごとの生データをそのまま順位表にしない。

人狼での利用例:

    const villagers = await KuroGames.ranking.get({
      mode: "werewolf_villager_wins",
      limit: 100
    });

    const wolves = await KuroGames.ranking.get({
      mode: "werewolf_wolf_wins",
      limit: 100
    });

この累計集計が本番APIで正しく動いているかは、同じユーザーの複数試合・別ユーザー・重複送信を使ったE2Eテストで確認する。GitHub上のEdge Functionソースと本番デプロイ版の同期も必要。

### 8.5 submissionIdと二重登録防止

- 各試合に一意なroundIdを付与する。
- 同じ試合結果の再送では同じsubmissionIdを使用する。
- DBにgameId、userId、mode、submissionId等の一意制約を設ける。
- SDKのranking.submitはoptions.submissionIdが渡された場合、それをAPIへそのまま渡す。未指定時だけSDKがUUIDを生成する。
- 2026-11-22修正済み: 共通SDKは有効なUUID形式のoptions.submissionIdをそのままAPIへ渡し、未指定または不正な場合のみUUIDを生成する。ゲームHTML側のキャッシュキーも更新して新SDKを読み込む。
- 重複登録を受けたときは、既存結果を二重加算せず、既登録であることを判別できる応答を返す。

### 8.6 不正対策と現在の限界

現行のscore_submitは、ログイン本人のスコアとして保存することと基本的な数値・サイズ・送信頻度を検証する。しかし、クライアントが申告したスコアがゲームルール上正しいかを一般的に証明するものではない。

したがって:
- クライアント送信スコアは未検証データとして扱う。
- ランキングの信頼性を必要とするゲームは、7章のサーバー側判定を実装する。
- サーバー検証のないランキングには「参考記録」等の扱いを設けるか、正式ランキングへの登録を停止する。
- 人狼の勝利回数も、最終的にはサーバー側が試合結果を確定してから登録する。

## 9. エラー形式・復旧ルール

APIのエラーはJSONで返し、ゲーム側は例外を捕捉する。

標準エラー例:

    {
      error: "このルームは満員です。",
      code: "ROOM_FULL"
    }

代表的なHTTPステータス:

| HTTP | 意味 | ゲーム側の対応 |
|---|---|---|
| 400 | 入力形式・値が不正 | 入力を修正 |
| 401 | 未ログイン・認証期限切れ | ログイン状態を更新 |
| 403 | 機能OFF・権限なし・非参加者 | 処理を中止 |
| 404 | ゲーム・ルーム・データが存在しない | 一覧や画面を更新 |
| 409 | 満員・重複・更新競合 | 最新状態を再取得 |
| 410 | ルーム終了・利用期限切れ | ルーム画面へ戻る |
| 413 | データサイズ超過 | 送信データを縮小 |
| 429 | 送信回数上限 | 少し時間を置いて再試行 |
| 500 | サーバー内部エラー | 状態を確定扱いせず再確認 |

再試行ルール:
- 送信がタイムアウトしたとき、失敗したと断定して別IDで同じ結果を送らない。
- 同じ論理操作の再送は同じactionId/submissionIdを使う。
- 二重決済・二重報酬・二重勝利加算を発生させない。
- 競合時は最新stateを取得して操作を再計算する。
- ネットワークが復帰したら、サーバーの確定状態を取得し直す。

## 10. セキュリティ・プライバシー必須ルール

- Supabase service role key、Cloudflareの秘密情報、秘密鍵をゲームHTML、SDK、公開リポジトリに書かない。
- アクセストークンをconsole.log、ゲームイベント、セーブデータ、URLに出さない。
- クライアントから送られたuserId、kuroId、rank、勝敗、所持アイテム数を信用しない。
- 全APIでgameIdと公開状態を確認する。
- ルームAPIではroomId、gameId、userId、参加状態を毎回確認する。
- 他人のセーブ、個人状態、管理者操作へアクセスできないようにする。
- ユーザー入力、イベント名、JSON構造、件数、サイズ、送信頻度をサーバー側で検証する。
- 秘密情報をログに残さない。
- APIエラーに内部SQL、キー、トークン、環境変数の値を含めない。
- 本番データをテストで破壊しない。テスト用ゲーム・ルーム・アカウントを使う。
- クライアント内の難読化や変数名変更はセキュリティ対策とみなさない。

## 11. ゲーム開発者向け実装テンプレート

公開情報だけで進行する簡単なルームゲームの例:

    const { features } = await KuroGames.init({
      gameId: "StudioのゲームID"

    if (!features.multiplayer) {
      throw new Error("このゲームではマルチプレイが無効です。");

    const room = await KuroGames.multiplayer.createRoom({
      maxPlayers: 4
    });

    const offPlayers = room.onPlayersChange((players) => {
      renderPlayers(players);
    });

    const offMessages = room.onMessage((event) => {
      if (event.type === "public-notice") {
        renderNotice(event.data);

    const snapshot = await room.getState();

    if (snapshot.state === null) {
      await room.updateState({
        phase: "lobby",

    // ゲーム終了または画面を離れる時

この例は公開状態だけを使うゲーム向けである。秘密の手札・役職・山札を扱うゲームへ、そのまま転用してはならない。

## 13. 受け入れテスト（本番公開前の必須条件）

### A. 認証・所有権
- 未ログインではオンライン機能を利用できない。
- ユーザーAはユーザーBのセーブを読めない。
- gameIdを差し替えて他ゲームのデータを読めない。
- bodyに他人のuserIdを入れても本人になりすませない。
- Studioで機能をOFFにするとAPI側も拒否する。

### B. ルーム
- ルーム作成、6文字コード参加、退出が正常。
- 2人から35人まで設定人数に従って参加できる。
- 36人目は拒否される。
- 満員・終了済み・期限切れ・別ゲームのコードを拒否する。
- 同じユーザーの重複参加を正しく処理する。
- 競合更新で古いstateが新しいstateを黙って上書きしない。

### C. 秘密情報
- AのNetworkレスポンスにBの手札が含まれない。
- AのNetworkレスポンスに未配布の山札が含まれない。
- Realtimeのbroadcastに秘密情報が含まれない。
- HTTPポーリング応答に秘密情報が含まれない。
- 公開ルーム状態を全取得しても秘密情報を復元できない。
- 他人の個人状態取得をAPIが拒否する。

- 自分のターンでない操作を拒否する。
- 存在しないカード・所有していないカードの操作を拒否する。
- 不正なフェーズでの操作を拒否する。

- クライアントの勝敗画面を書き換えてもランキングを変更できない。
- サーバーが確定した勝者とランキング記録が一致する。

### E. ランキング
- submit後にgetで記録を取得できる。
- 別modeの記録が混ざらない。
- limitの上限が守られる。
- 同点時の順序が安定する。
- 同じsubmissionIdの再送で二重加算されない。
- 人狼の村人勝利と人狼勝利が別々に集計される。
- 1人の複数試合の勝利数が正しく合算される。
- 敗北・観戦・途中退出で勝利数が増えない。
- サーバー検証なしのクライアント申告だけでは正式な勝利数を確定しない。

### F. Cloudflare relay / Durable Objects
- 上記A〜Eのテストを両通信方式で実施する。
- HTTPフォールバックの遅延・再送・重複通知があってもゲーム状態が破損しない。
- どちらの方式でもSDK利用コードを変更しなくてよい。

## 16. 完成の定義

KUROGAMES共通オンライン基盤は、次のすべてを満たした時点で「安全なオンラインゲーム基盤として完成」とする。

- SDKのAPIと戻り値が仕様書と一致する。
- Cloudflare経由の通信とDurable Objectsの接続が、共通SDKの契約どおりに動作する。
- 公開情報・個人情報・サーバー専用情報の境界が守られる。
- 他人の手札・役職・秘密データをクライアントから取得できない。
- 重要なゲーム操作、勝敗、報酬をサーバーが検証する。
- 同じ操作や試合結果を再送しても二重処理されない。
- ランキング登録とランキング取得が両方動作する。
- 正式ランキングにはサーバーが検証した結果だけが登録される。
- 35人ルーム、通信切断、再接続、同時更新、エラー時のテストに合格する。
- GitHubのソース、実際のデプロイ、SDK配信ファイル、Studioの説明文が同じ仕様を示している。

**この完成条件を満たすまでは、共通SDKの通信機能が存在することと、秘密情報や勝敗まで安全に保護されたことを同じ意味で扱わない。**


## 17. サーバー実行基盤とゲーム固有ルールの責任分担（正式方針）

この節は推奨案ではなく、KUROGAMESオンライン基盤の正式な設計・開発方針とする。

### 17.1 基本原則

**KUROGAMESが共通のサーバー実行基盤を開発・運用し、ゲーム制作者がゲーム固有のルールと判定ロジックを定義する。**

ゲーム制作者に、認証基盤、データベース、ルーム管理、通信サーバー、ランキング基盤を個別に構築させない。これらの共通機能はKUROGAMESが提供する。

一方、ゲームごとに異なる合法手、ターン進行、勝利条件、得点計算などを共通基盤が推測してはならない。これらはゲーム制作者が定義したゲーム固有ルールとして、サーバー実行基盤上で実行する。

### 17.2 KUROGAMESが開発・運用する共通基盤

KUROGAMESの責任範囲は以下とする。

1. ゲーム固有サーバー処理を実行する隔離されたサーバー実行環境を提供する。
2. ゲーム別ルールモジュールの登録、バージョン管理、公開・停止を行う。
3. 認証済みユーザー、KURO ID、gameId、roomId、セッションを検証する。
4. ルーム作成、参加、退出、ホスト権限、接続状態を管理する。
5. 公開ルーム状態、個人専用状態、サーバー専用状態を分離して保存する。
6. ゲーム処理に渡す入力と、ゲーム処理から返る状態・イベントを検証する。
7. 操作ID・バージョン番号・トランザクション等を用いて同時実行と二重処理を防ぐ共通機構を提供する。
8. サーバー確定結果をランキング・セーブ・ルーム状態へ安全に反映する。
9. 実行時間、メモリ、データサイズ、リクエスト頻度等に上限を設ける。
10. ゲーム別処理のエラー隔離、監査ログ、監視、停止・ロールバック機能を提供する。
11. Cloudflare経由の各APIとDurable Objectsで同じSDK契約・権限境界・結果形式を維持する。
12. ゲーム制作者向けのSDK、API仕様、サンプル、テンプレート、テスト環境を提供する。

共通基盤はゲーム固有コードを安全に実行する責任を持つが、ゲーム固有ルールの正しさを自動的に創作・保証するものではない。

### 17.3 ゲーム制作者が定義・実装するゲーム固有ルール

ゲーム制作者の責任範囲は以下とする。

1. ゲームの状態構造と状態遷移。
2. プレイヤーが実行できる操作の種類。
3. 各操作の入力形式と合法条件。
4. ターン、フェーズ、時間制限の進行条件。
5. カード・アイテム・ポイント等の所持・消費ルール。
6. 乱数を必要とする場合の抽選条件と結果の意味。
7. 勝利・敗北・引き分けの条件。
8. スコア、勝利回数、報酬の計算方法。
9. どの情報を全員に公開し、どの情報を本人だけに見せ、どの情報をサーバー内に留めるか。
10. ゲーム終了・途中退出・切断時の扱い。

ゲーム制作者は、これらをKUROGAMESが定めるサーバー側ルールモジュールのインターフェースに従って実装する。クライアント側JavaScriptにしか存在しない判定処理は、サーバー検証済みの判定として扱わない。

### 17.4 サーバー側ルールモジュールの標準契約

KUROGAMESは、ゲーム固有モジュールが共通基盤から呼び出されるための安定したインターフェースを定義する。実際の関数名・ランタイム・パッケージ形式は実装時に確定し、SDK/API仕様書と開発テンプレートに反映する。

最低限、次の処理を表現できること。

- ゲーム開始時の初期状態生成
- プレイヤー参加・退出時の処理
- プレイヤー操作の検証と適用
- ターン・フェーズの進行
- サーバー側乱数を必要とする処理
- 勝敗・スコア・報酬の確定
- 公開情報、本人専用情報、サーバー専用情報の分割
- ゲーム終了時の確定処理

モジュールが受け取るプレイヤーIDや権限情報は、KUROGAMESが認証・検証したコンテキストから渡す。クライアント入力に含まれるuserIdやkuroIdを本人確認の根拠として渡してはならない。

モジュールは、検証済みの操作結果と状態変更案を返す。永続化・ランキング登録・イベント配信は共通基盤が権限と整合性を確認したうえで確定する。

### 17.5 標準的な処理フロー

1. クライアントが共通SDKでゲームを初期化する。
2. プレイヤーがルームを作成または参加する。
3. KUROGAMESが認証、gameId、roomId、参加状態を検証する。
4. KUROGAMESがゲームセッションを発行する。
5. 共通基盤がゲーム固有モジュールを呼び出し、サーバー側で初期状態を作る。
6. クライアントは操作要求と一意なactionId、必要なexpectedVersionを送信する。
7. 共通基盤が認証、参加権限、入力サイズ、レート制限、重複、バージョンを検証する。
8. ゲーム固有モジュールが合法手・ターン・ゲームルールを検証して操作を適用する。
9. 共通基盤が状態変更を整合性を保って保存する。
10. 共通基盤が公開情報だけを全員に配信し、個人情報は対象プレイヤーにだけ返す。
11. ゲーム固有モジュールが勝敗条件を満たした場合、サーバー側の確定結果を返す。
12. 共通基盤が結果を一度だけ記録し、必要なランキングを更新する。
13. クライアントはサーバー確定結果を表示する。

### 17.6 権限・安全境界

- ゲーム固有モジュールは、認証済みコンテキストと許可されたAPIだけを使用する。
- ゲーム固有モジュールからも、他ゲームのデータや他ルームの秘密情報へアクセスできないようにする。
- サーバー専用状態はクライアント用シリアライズ処理に含めない。
- 個人専用状態は対象本人向けのレスポンス以外に含めない。
- クライアントが送信した勝敗、スコア、役職、手札、報酬を確定値として採用しない。
- サーバー実行環境では、秘密鍵やサービスロール資格情報をゲーム制作者のコード・クライアントへ露出させない。
- ゲーム別モジュールの実行権限・時間・メモリ・ネットワークアクセスは制限する。
- モジュールのバージョンと各試合の利用バージョンを記録し、進行中の試合でルールが途中変更されないようにする。

### 17.7 Studioでの開発・登録体験

将来のKUROGAMES Studioでは、ゲーム制作者が次の流れでサーバー判定を利用できるようにする。

1. オンライン設定で「サーバー検証」を有効にする。
2. ゲームの種類に合ったサーバールールテンプレートを選ぶ。
3. Studioのエディターまたはファイル読み込みでゲーム固有ルールを定義する。
4. 公開情報・個人専用情報・サーバー専用情報を指定する。
5. テストルームで正常操作、不正操作、同時操作、切断を検証する。
6. 検証に合格したルールモジュールをバージョン付きで公開する。
7. 対象ゲームのセッションは公開済みのモジュールを使用する。

テンプレート・エディター・サーバールール登録画面は、実装されるまでは「今後実装」と扱う。画面や仕様書に記載しただけで利用可能と表示してはならない。
